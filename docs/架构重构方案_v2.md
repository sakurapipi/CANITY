# CANITY 架构重构方案 v2

> v1 是"按直觉设计"，v2 是"按证据设计"。
> 结论先给：**v1 的方向对，但顺序错了、收益估高了、还漏了一个 4,707 行的测试文件。**

---

## 0. 三句话结论

1. **先做零代码的三件事**（卡片 / 清单 / 范围锁），再谈搬文件 —— 文献证据显示"外部检查清单"把成功率从 5/10 拉到 10/10，而重构只省 token、几乎不提高正确率。
2. **重建议顺序**：卡片 → 测试拆分 → 域搬迁 → 表驱动。**不建事件总线，不建 core 框架。**
3. **收益从 v1 的"降 85%"下调到"降 40~60%"** —— 文献实测是 17~39%，本项目因为 game.c 占 48% 的提交，上限更高，但不会是 85%。

---

## 1. 证据（这一节是新加的，v1 没有）

### 1.1 文献：代码地图类工作流到底省多少

[How Should Agents See Code?（arXiv 2611.07286）](https://arxiv.org/abs/2611.07286) 在四个仓库级基准上跑了 5 种代码表示工作流：

| 基准 | 结果 |
|---|---|
| LinuxFLBench（故障定位） | recall@10 **0.717 → 0.757~0.829**，token **−25~39%** |
| SWE-bench Pro（改代码） | 解决率 **44.3~50.6% vs 49.0%**（基本持平），token **−17~26%** |
| SecBench（安全补丁） | 补丁解决率 34.3% vs 28.9%，token 更少 |
| SWT-bench（写测试） | **token 反而更多**，更慢 |

**三条直接可用的结论**：

1. 代码地图/模块依赖类工作流，**在"定位是瓶颈"时才是省钱工具**，到达改代码阶段收益就收窄了。
2. 收益是 **17~39%** 这个量级，不是我 v1 说的 85%。
3. **不是所有任务都省** —— 写测试那种反而更贵。所以"全面重构"没有意义，要挑任务类型。

### 1.2 文献：光变小文件不解决"漏项"

[When and How Context Rot Appears in Coding Agents（arXiv 2607.17937）](https://arxiv.org/html/2607.17937v2) 的白盒实验：

```
干净上下文 10,991 字符   → 10 次里过 8 次
长上下文   299,140 字符  → 10 次里过 3 次   （失败率 20% → 70%）
```

但**要求覆盖率仍有 0.933~0.949** —— 也就是说：

> **不是"做不出来"，是"漏掉了几条决定性的要求"。**

而且 44 次失败里有 **38 次仍然宣称自己完成了**（silent completion）。

**最有价值的一条**：同一长上下文下，

```
笼统地让 agent "自查一遍"        → 10 次过 5 次
给一份写明 24 条义务的外部清单   → 10 次过 10 次   (p = 0.0325)
```

**这是整份资料里性价比最高的干预**：一份清单，零代码改动，成功率翻倍。

### 1.3 文献：上帝类确实更贵

Khomh 等人的研究（[ICSM/EMSE](https://dl.acm.org/doi/pdf/10.1145/1985362.1985366)）跟踪三个开源系统的演化，
发现 god class 的**变更频率显著高于普通类**（文中量级是十几倍 vs 个位数）。

我们这边量出来是 **48% 的提交都要碰 game.c** —— 同一件事，规模小一点，方向一致。

## 2. 本项目实测（v1 没有的第二个证据）

### 2.1 改动局部性（最近 60 次提交）

```
每次提交改动的文件数：中位数 4，平均 4.9，最大 29
单次提交涉及的文件总行数：中位数 11,004，平均 16,161
                         ≈ 100k ~ 145k token / 次（如果都读一遍）

文件出现频率：
  src/game.c            48%   ← 一半的改动都要碰它
  tests/test_runtime.c  38%   ← ★ v1 漏了这个
  src/ui.c              27%
  web/shell.html        20%
```

### 2.2 v1 漏掉的那个：`tests/test_runtime.c` = **4,707 行**

一次典型改动的必读量：

| 文件 | 行数 |
|---|---|
| src/game.c | 9,556 |
| **tests/test_runtime.c** | **4,707** |
| include/common.h | 1,252 |
| 合计 | **15,515 行 ≈ 140k token** |

**只拆 game.c 不动测试，等于只解决了一半。** 这是 v2 最重要的修正 —— 测试也要按域拆。

### 2.3 已拆域的"必读量"（`tools/module_cost.py` 实测）

```
throwing  744 行 ✅   hatch     259 行 ✅   skills   1,007 行 ✅
shop    1,058 行 ✅   warden  1,133 行 ✅   lockbox  1,219 行 ✅
ui      5,590 行 ✗   render  4,283 行 ✗
```

**你的模块本身不烂，烂的是 game.c 和 test_runtime.c 这两个没有边界的大文件。**

## 3. v1 → v2 的五处修正

| # | v1 的说法 | v2 改成 | 依据 |
|---|---|---|---|
| 1 | 先建 `core/` 四件套（tick/事件/RNG/存档分区） | **不建框架**。只保留 tick 表 + RNG，事件用"回调数组"，存档分区推迟 | 文献：写测试类任务重构反而更贵；框架建设是经典过度设计 |
| 2 | 收益降 85% | 收益 **40~60%** | 文献实测 17~39%；本项目上限更高但不会是 85% |
| 3 | 先搬 phase/hatch/collapse | **先做卡片 + 清单 + 范围锁（零代码）**，再拆测试，最后才搬 | 文献：清单 5/10→10/10，比搬文件便宜得多 |
| 4 | 测试不用动 | **测试必须按域拆**（4,707 行，38% 的提交都要读） | 本项目实测 |
| 5 | 事件总线是核心 | **降级为"静态回调表"**，不做泛型 payload | C 语言里泛型事件是长期负债；实际只有 4 个联动点 |

## 4. 修订后的架构（比 v1 薄一半）

```
┌──────────────────────────────────────────────────────────┐
│ content/   数据表：投掷物 / 技能 / 遗物 / 房间             │  加内容=加一行
├──────────────────────────────────────────────────────────┤
│ domain/    每个域：x.h(≤120行) + x.c(≤800行) + CARD.md     │
│            test_<域>.c(≤300行)                            │
├──────────────────────────────────────────────────────────┤
│ core/      **只有两个东西**（合计 ≤200 行）                │
│            · tick 表（顺序表，12 行）                      │
│            · rng（固定 seed，可复现）                      │
├──────────────────────────────────────────────────────────┤
│ include/   契约                                                │
└──────────────────────────────────────────────────────────┘
```

**v2 砍掉的**：通用事件总线、存档分区、四层严格依赖、域间只读查询层。
**理由**：它们各自的收益在文献里没有证据支持，而成本是真实的（每个都要写、要测、要维护）。

## 5. 可行性逐项评估（C 语言视角）

| 改造项 | 运行时开销 | 风险 | 可行性 | 结论 |
|---|---|---|---|---|
| **模块卡片** | 0 | 无 | 100% | ✅ 立刻做 |
| **任务清单 + 范围锁** | 0 | 无 | 100% | ✅ 立刻做 |
| **tick 顺序表** | 12 次间接调用/帧 ≈ 纳秒级 | 极低 | 100% | ✅ 做 |
| **固定 RNG** | 一次乘法 | 低（要改所有 `rand()` 调用点） | 95% | ✅ 做（顺带修 AD-64 的根因） |
| **表驱动投掷物** | 一次数组索引 | 中（13 种 × 3 段行为要对齐） | 90% | ✅ 做，但**先补测试** |
| **测试按域拆** | 0 | 低（纯搬运） | 100% | ✅ 做 |
| **域搬迁（phase/hatch/collapse）** | 0 | 低（纯搬运） | 100% | ✅ 做 |
| 通用事件总线 | 每次事件一次间接调用 | **中高**（生命周期、重入、C 里无类型安全） | 70% | ❌ 不做 |
| 存档分区 | 0 | 高（序列化兼容，5 个历史档是唯一防线） | 80% | ⏸ 推迟到真需要时 |
| ui 拆页（5,542 行） | 0 | 中（页面间共享状态多） | 85% | ⏸ 推迟（27% 的提交，但改动浅） |
| render 重构 | **高**（每帧几十万像素） | 高 | 30% | ❌ 永不做 |

> 一句话：**C 语言里任何"增加间接层"的设计都要付运行时和心智双重成本。
> 只加那些"每帧只跑一次"的间接层（tick 表），绝不在热点路径上加速抽象。**

## 6. 效率账（这才是你要的"省多少"）

### 6.1 现状：一次典型改动

```
必读：game.c 9,556 + test_runtime.c 4,707 + common.h 1,252 = 15,515 行
     ≈ 140k token（按 9 token/行估）
再加"定位"的来回工具调用 ≈ 1.5~2 倍 → 实际 200k~280k token/次
```

### 6.2 改完之后（理想单域任务）

```
卡片 40 + 契约 120 + 实现 800 + 该域测试 300 = 1,260 行 ≈ 11k token
```

**理论上 −92%。**

### 6.3 但现实是（文献校准）

| 任务类型 | 文献实测 | 本项目预期 |
|---|---|---|
| 定位型（"投掷物落地在哪"） | −25~39% | **−55~70%**（game.c 占 48% 提交，收益高于平均项目） |
| 改代码型（"加一个投掷物"） | −17~26% | **−40~55%** |
| 跨切面型（web + platform + 存档） | 0 ~ 更多 | **0**（这类改动本来就散，重构帮不上） |

**综合预期：中位数改动 −45%，不是 −85%。**

写成一句你能记住的话：

> **重构不是让所有任务都变便宜，是让"高频且集中"的那一半任务便宜一半以上。**

### 6.4 但正确率不靠重构

文献最硬的一条：**重构不提高成功率，清单才提高。**

```
清单 + 范围锁（零代码）  → 成功率 5/10 → 10/10
重构（搬文件/拆表）      → 成功率基本不变，只降 token
```

所以 v2 把"零代码三件事"排在第一轮，**第一轮就能拿到正确率收益，不用等重构做完。**

## 7. 路线（8 轮，比 v1 少 1 轮，但第一轮就能见效）

| 轮 | 内容 | 代码改动 | 预期效果 |
|---|---|---|---|
| **1** | **卡片 ×5 + 任务清单模板 + 范围锁接 CI + 成本测量进 CI** | **0 行** | 漏项率下降；我干活有边界 |
| **2** | 测试按域拆：`test_runtime.c` 拆出 phase/hatch/collapse/throwing 四个域测试 | 纯搬运 | 38% 的提交少读 4,000 行 |
| **3** | phase + hatch + collapse 搬家（game.c −950 行） | 纯搬运 | 48% 的提交里那部分便宜一半 |
| **4** | tick 表 + 固定 RNG 接入 | 小 | 帧顺序可查；地形可复现 |
| **5** | 投掷物：先补 13 种 × 3 段行为测试 | 0（只加测试） | 现状锁死 |
| **6** | 投掷物换表驱动 | 有 | 加道具 = 加一行 |
| **7** | UI 拆页（可选） | 纯搬运 | 27% 的提交受益 |
| **8** | 收口：文档、CI 指标、全量回归 | — | — |

**第 1 轮就能验收"省不省"** —— 不用等 8 轮。

保守估计 **10 轮**（含 2 轮回归缓冲）。v1 是 9~12，v2 是 **8~10**。

## 8. 验收指标（可量化，进 CI）

```bash
python tools/module_cost.py --budget 2500     # 单域必读量 ≤ 2,500 行
python tools/check_scope.py --allow <域>       # 改动不出域
python tools/budget_check.py --median 2500    # 最近 20 次提交的"改动涉及行数"中位数 ≤ 2,500
python tools/build_validate.py                # 12,212 checks 不降
```

第三条是新加的 —— **把"改动局部性"本身变成 CI 指标**，比任何架构图都实在。

## 9. 不要做的事（比做什么更重要）

| 别做 | 为什么 |
|---|---|
| 建通用事件总线 | C 里没有类型安全，4 个联动点不值得一套框架 |
| 拆 render.c | 每帧几十万像素的热点，收益 0，风险最高 |
| 拆 cjk_glyphs.c | 纯字模数据，零逻辑 |
| 动存档布局 | 5 个历史档是唯一防线，加字段的收益 < 风险 |
| 追求"全库零 extern" | 440 个 extern 里大部分是只读查询，改成 accessor 只是换写法 |
| 一次大重构 | 文献里的失败案例全是"一次搬完"。**每轮一个可回滚的提交** |

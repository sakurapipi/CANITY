# 2.4.2 RC 已知接受偏差（2026-11-10）

> 本文件记录 **build_validate 仍会失败、但用户已审核确认"不修"** 的断言。
> 目的：让后来的人（和 CI 日志的读者）知道这 4 条是**接受的偏差**，不是"忘了修"。

## 背景

审计发现验收链有 7 条失败。修复轮把其中 3 条修掉，剩余 4 条：

```
VALIDATION SUMMARY: 22 passed / 4 failed     （partition: OK）
```

用户与实现方（Codex）核对后确认：**这 4 条断言检验的设计，与用户当前的需求已经不一致**，
因此不修改断言、也不修改实现。

## 4 条接受偏差清单

| # | 断言（build_validate 输出） | 位置 | 判定 |
|---|---|---|---|
| 1 | `keyboard can reach alternative capstones in the new graph` | `tests/…:973` | 技能树改版后，键盘可达性检查仍按旧图结构判定；新图的可达性以鼠标/新导航为准 |
| 2 | `the first light beast must spawn` | `tests/…:411` | 刷怪节奏已改为"层数/威胁驱动"，不再保证"第一只光兽必出" |
| 3 | `a floor must only contain the themes allowed at that depth` | `tests/…:152` | 主题房间改为"由层场景主题决定"，旧的层数白名单分组已废弃 |
| 4 | `test fixture: two-chunk payload must pack` | `tests/…:510` | 存档分块打包的夹具假设与当前 payload 尺寸不符，夹具未重做 |

> 位置行号仅作定位提示；以 `python -X utf8 tools/build_validate.py` 的实际输出为准。

## 影响

```
· build_validate 仍会以非 0 退出
· GitHub CI 的 "Build and validate" 步骤仍会红
· 因此 "Build and Release" 工作流不会自动产出 Release / 安装包
```

**这是已知且接受的代价**，不是回归。

## 如果需要 Release

两条路：

1. 把 4 条断言按新设计重写（等于承认新设计为基线）；
2. 本地 `tools/package_release.py` 打包后，手动创建 GitHub Release 上传 zip。

## 变更纪律

- 本文件只记录"已接受"，**不等于**这 4 条永远不能修；
- 若后续设计回退到旧行为，应删除对应条目并恢复断言；
- 新增的"接受偏差"必须写进本文件，不允许只在聊天里说一句。
